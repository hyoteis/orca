# clangd topology for mapped compile databases

**Research date:** 2026-09-07
**Research ticket:** [Evaluate clangd topologies for mapped compile databases](https://github.com/hyoteis/orca/issues/121)
**Sources:** LLVM main-branch sources (retrieved 2026-09-07), clangd 12 release notes, clangd.llvm.org docs, LLVM/Chromium first-party usage data, and LLVM issue tracker (see [Sources](#sources)). Builds on prior research: [clangd multi-folder aggregation](https://github.com/hyoteis/orca/issues/41), [merge and reload semantics](https://github.com/hyoteis/orca/issues/22), [clangd without a CDB](https://github.com/hyoteis/orca/issues/17) — their facts are cited, not re-derived.

## Verdict (ranked)

1. **T1 — one clangd session, one Orca-merged aggregate CDB in Orca host cache, `--compile-commands-dir=<that dir>`.** The only topology that delivers the #119 contract ("mapped folders interoperate") without new client plumbing: one unified in-memory index makes cross-folder definition/references immediately consistent, all shards land under the Orca cache dir, reload is lazy-but-incremental, and per-TU failures below the JSON-parse level cannot poison other entries. It is also exactly the mechanism Orca already ships (merged shards in scope cache + FixedDir + spawn-time existence assert), so the #119 design replaces entry *provenance* (CMake/GN generation → user-supplied DBs + BASIC synthesis), not the topology.
2. **T3b — BASIC folders in the same session and the same aggregate.** BASIC is not a second topology: Orca already synthesizes `clang/-std/-D/-I` commands for BASIC members (`code-intelligence-compilation-database.ts`) and merges them into the same file (`code-intelligence-cpp-setup-generation.ts`). Sharing one session gives BASIC folders background indexing for free and keeps one client, one status surface. Include it in T1.
3. **T2 — one session per mapping.** Rejected for the product contract: separate clangd processes hold indexes that "know nothing about each other" (maintainer), so cross-folder navigation disappears unless Orca builds client-side fan-out/merge/ambiguity resolution that does not exist today; index memory for headers shared across mappings duplicates per session. Its one genuine win — crash isolation — is already mitigated for T1 by single-flight session re-open.
4. **T3a — per-folder config `CompileFlags.CompilationDatabase` scoping via `If.PathMatch`.** Rejected under Orca's constraints: there is no injection point that keeps config in Orca cache (no `--config-file` CLI flag exists; project `.clangd` discovery would require writing into user trees, user config dir is cross-workspace pollution), and shards would land next to each *supplied* DB (`SourceRoot` = that DB's dir), violating "aggregate/generated data only in Orca-managed cache". It also needs clangd ≥ 12 where the CLI flag does not.

Two *spellings* of one TU in one DB can instead make lookup ambiguous and fail outright. | SRC | [S2][S3] |

| F8 | Failure semantics, entry level: a TU whose main file can't be read or compiled fails inside its own queue task (`elog("Indexing {0} failed")`); tasks are independent and even shuffled. One bad TU/entry does not affect others. | SRC | [S4] |
| F9 | Failure semantics, file level: the JSON CDB parse is **all-or-nothing** — one unknown key, malformed shape, or broken JSON aborts the whole file (`return false` + `ErrorMessage`). Deleted CDB file → `Unloaded compilation database` → same graceful null. Partial writes are treated as transient (old CDB kept, retried). | SRC | [S2][S1] |
| F10 | Aggregate corruption blast radius: since the aggregate is Orca-authored, F9's whole-file failure is Orca's to prevent, not clangd's — validate each supplied DB (existence, shape, ≥1 in-folder command) before merging, keep last-valid entries per mapping on later deletion/corruption, and replace atomically. Then a degraded mapping is invisible to clangd and other mappings keep exact commands. Recovery latency after Orca rewrites a valid aggregate: ≤ 5 s (cache-populated path). | SRC+contract | [S2][S1][S3-int] |
| F11 | Session-level failure (T1's real exposure): one clangd process serves all mappings, so a crash/OOM takes everything down until re-open (single-flight re-open already exists). No per-mapping isolation — the only structural advantage of T2. | SRC+intern | [S9-int][S14] |

T1 therefore works on any clangd Orca can realistically launch; T3a would add a ≥ 12 requirement for no benefit. | DOC+intern | [S13][S8][S14] |

## What each topology implies, briefly

**T1 (recommended).** Indexing: single background index over the merged corpus; shards all in Orca cache (F1/F2). Reload: Orca watches supplied DBs, re-merges, atomically replaces; clangd converges ≤ 5 s, no-op rewrites are free, only changed-file entries re-enqueue, and flag-only changes keep old shards (F3–F5) — Orca must not advertise instant re-index for flag-only edits. Duplicates: Orca decides precedence and emits one canonical entry per TU, first-wins by array order; dual spellings are forbidden (F6). Navigation: unified cross-folder index (F7). Failure: entry-level isolation is perfect (F8); file-level failure is total-but-graceful and is Orca's to prevent via validation + last-valid retention (F9/F10); process crash is the shared fate (F11). Scaling: one process, one index, linear in aggregate TU count (F12) — keep the enumeration cap and add an RSS guardrail decision in #127.

**T2 (rejected).** Cross-folder navigation — the #119 contract's core — requires Orca to fan requests across N clients, merge results, and resolve duplicate symbols client-side; upstream says the processes share nothing (F7). Shared external headers are re-indexed and re-held per session (F12). The session infra (sessionId-keyed maps, per-session launch requests) already supports N sessions, so nothing *blocks* T2 — but the renderer's cpp session (`ensureClient` single-flight, one client per scope) has no multiplexing layer. Only worth revisiting as a per-mapping *escalation* guardrail if a pathological aggregate proves unmanageable in one process.

**T3a (rejected).** Mechanically possible (F13) but violates two product invariants: config fragments can't live in Orca cache, and shard placement follows each supplied DB's directory (F2). No CLI injection point exists.

**T3b (fold into T1).** BASIC entries are Orca-synthesized commands in the same aggregate — shipped behavior today. BASIC + mapped in one session is therefore the default, with BASIC fidelity permanently "approximate" per #17; that labeling is #126's concern, not a topology fork.

## Facts later decisions depend on

**#124 (session architecture)** must decide, on top of F1–F7/F13–F15:

- One session per (executionHost, workspace) cpp scope, as today; the launch carries only the cache `--compile-commands-dir`; per-mapping data lives entirely in the aggregate file, so *member/mapping edits never restart the session* (the existing `launchConfigurationPayload` split already encodes this).
- Aggregate construction: validate each supplied DB host-side; normalize to `arguments`-only, known keys only (F9 makes a single stray key fatal); one canonical native spelling per TU with explicit cross-DB precedence (F6); deterministic byte-stable ordering so content-digest suppression makes unchanged re-merges free (F3); atomic temp+rename in the cache dir.
- Upstream DB watching is Orca's job (F3: clangd never watches); manual reload = force re-merge + rewrite.
- BASIC folders join the same aggregate (T3b).

**#126 (authorization, degradation, status)** must decide, on top of F8–F12:

- Mapping-degradation granularity is Orca-side: last-valid entry retention per mapping; clangd never observes the failure (F10), so "degraded" is purely an Orca status + stale-commands honesty problem.
- Aggregate-level failure (should never happen; bug door): all mappings drop to fallback flags gracefully, no crash, no ancestor-search escape (F9) — recovery is a valid rewrite, ≤ 5 s pickup.
- Flag-only upstream changes refresh open-file ASTs but not shards (F4): status copy must not promise re-indexed symbols.
- Session crash takes all mappings down (F11): needs a restart policy and, in #127, memory guardrails informed by F12 (2.7 GB at Chromium scale in one process; 50 k TU budget today).
- Removed-mapping entries vanish from the corpus but their symbols persist in the session index until restart (prior fact M16, #935) — cosmetic staleness, acceptable.
